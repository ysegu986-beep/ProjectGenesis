# Genesis 試作と改善の進め方

Genesis は、作って、触って、違和感を見つけて、直す。

最初から正解を出そうとしない。

ただし、同じ失敗を何度も繰り返さない。

## 今回分かったこと

### 1. 文書があっても、遊べなければ意味がない

設計思想やカードリストは大事。

でも、ゲームは触って初めて分かる。

次からは、文書を増やすだけで終わらせず、必ず「触れる形」に近づける。

### 2. 最初の1分が詰まるとゲーム以前になる

最初のプロトタイプでは、マナチャージ後に何をすればいいか分かりにくかった。

また、マナに置くカード次第で1ターン目に何もできなくなった。

これはカードバランス以前の問題。

最初の体験では、プレイヤーが自然に次の行動へ進めることを優先する。

### 3. ログより盤面で分かるべき

ログは補助。

何が起きているかは、できるだけ盤面、カード、ボタン、フェーズ表示で分かるようにする。

### 4. 指示待ちだけでは足りない

ユーザーに言われたことだけを実装しても、良いものにはならない。

違和感が見えたら、こちらから原因を探し、仮説を立て、直す。

ただし、勝手に大きく方向転換しない。

## 次から守ること

### 触れるものを先に出す

カードゲームの試作では、まず以下が通ることを確認する。

- マナに置ける
- カードを使える
- 攻撃できる
- シールドが減る
- ターンが返ってくる
- 勝敗まで行ける

### 初回手札は体験優先でよい

最初のテストでは、完全ランダムより「基本の流れを体験できる手札」を優先してよい。

ランダム性の検証は、その後で行う。

### 詰まったら、まず原因を分ける

問題が出たときは、すぐ大きく作り直さない。

まず次のどれかに分ける。

- UIが分かりにくい
- ルールが分かりにくい
- カードが噛み合っていない
- 実装がバグっている
- そもそも体験が弱い

### 1回の修正で変える範囲を絞る

一度に全部直すと、何が良くなったか分からなくなる。

1回の修正では、できるだけ1つの問題に集中する。

## アーク側の役割

アークは、ただ指示を待つだけにしない。

やること:

- 触って確認する
- 詰まりを見つける
- 原因を言語化する
- 最小の修正を入れる
- 修正後にもう一度触って確認する
- 学びを文書に残す

やらないこと:

- 見た目だけ整えて遊べないものを出す
- ログだけでゲームが進んだ気になる
- ユーザーに言われた問題だけを直して満足する
- 触って確認せずに「できた」と言う
